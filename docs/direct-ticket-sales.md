# Прямая продажа билетов STATUS TEAM: реализация и запуск

Ветка добавляет автономный сервер `ticketing/` к существующему статическому Next.js.
Сайт остаётся статическим (`output: export`), его дизайн и текущая предзапись сохраняются.
Платёжные ключи, SMTP и база не попадают в браузер или в каталог `out/`.

## Что уже работает

- Страница покупки с категориями, количеством, email и серверной ценой.
- Транзакционное резервирование количества: параллельные заказы не превышают остаток.
- Идемпотентное создание заказа и платежа, восстановление после неопределённого ответа.
- Локальная имитация оплаты без карты, а также адаптер **тестовой** ЮKassa.
- Проверка платежа запросом к API: сумма, валюта, принадлежность заказу и `test: true`.
- По одному уникальному QR на каждый билет; HTML-билет, печать / сохранение PDF браузером.
- Письмо со ссылкой на билеты через SMTP, постоянная очередь, повторные попытки и отправка из админки.
- Страница `/staff`: заказы, проверка оплаты, полный возврат, повторная отправка, контроль входа.
- Атомарный проход: два одновременных сканирования одного билета дают ровно один проход.
- Полный тестовый возврат: блокировка входа на время возврата, аннулирование после подтверждения.
- Фоновая сверка неоплаченных заказов и возвратов раз в минуту — на случай потери webhook.

**Это проверяемая тестовая версия, а не открытые продажи.** Live-провайдеры и реальные
ключи запрещены кодом. `SALES_OPEN` оставлен `false`. Фискализация пока не реализована.
Все страницы и письма явно маркированы тестовыми; билеты не действуют на мероприятии.

## 1. Проверить локально

Требуется Node.js 24+. База использует встроенный `node:sqlite`. Команды из корня проекта:

```bash
npm ci --prefix ticketing
cp ticketing/.env.example ticketing/.env
```

В `ticketing/.env` задайте случайный `TICKETING_STAFF_PASSWORD` длиной от 24 символов.
Не присылайте его в чат и не коммитьте. Затем:

```bash
npm start --prefix ticketing
```

Откройте `http://127.0.0.1:4320`. Создайте заказ, выберите имитацию успешной оплаты,
откройте QR-билет. Служебная страница: `/staff`, логин `staff`, пароль из окружения.
Проверьте проход, повторное сканирование, отдельный возврат ещё не использованного билета.
Если SMTP не настроен, письмо не отправляется и интерфейс не сообщает об успешной доставке.

```bash
npm test --prefix ticketing
npm run typecheck
npm run lint
npm run build
```

Mock-режим разрешён только с локальным `TICKETING_BASE_URL`; не публикуйте его через туннель
или reverse proxy. Для публичного тестового стенда используйте `yookassa-test`.

## 2. Где размещать на Beget

Рекомендуемая схема для этой реализации:

- `statusteam.<ваша-зона>` — статическая сборка `out/`, обычный хостинг Beget.
- `tickets.statusteam.<ваша-зона>` — отдельный Node.js-сервер `ticketing/` на VPS Beget.
- База — на локальном диске этого VPS, вне веб-корня; один экземпляр приложения.

VPS здесь выбран для управляемого процесса Node.js, фоновой сверки и локальной SQLite.
Это не утверждение, что Node.js невозможен на обычном хостинге: Beget описывает
его запуск через Docker/Passenger, но такой режим для этого сервиса **не проверялся**.
Версию Node и работу SQLite на конкретном тарифе необходимо проверять отдельно.

Официальные инструкции Beget:

- [Установка Node.js на хостинге](https://beget.com/ru/kb/how-to/web-apps/node-js).
- [Управление сайтами и переход к файлам](https://beget.com/ru/kb/manual/sajty).
- [Домены, поддомены и SSL](https://beget.com/ru/kb/manual/domeny-i-poddomeny).
- [Принцип reverse proxy Nginx на VPS](https://beget.com/ru/kb/how-to/vps/kak-nastroit-balansirovku-nagruzki-na-servere-pri-pomoshchi-nginx).

### Сайт

Соберите `npm run build`, загрузите **содержимое** `out/` в папку сайта через файловый
менеджер Beget. Привяжите домен, включите HTTPS. Исходники, `.env`, `ticketing/` и базу
в публичную папку не загружайте. Сами по себе статические файлы не запустят сервер продаж.

### Сервер тестовых продаж

На VPS подготовьте Node.js 24, Nginx, HTTPS-сертификат и отдельного системного пользователя
`statusteam`. Разместите репозиторий в `/srv/statusteam` и установите зависимости:

```bash
cd /srv/statusteam
npm ci --prefix ticketing --omit=dev
```

Создайте `/var/lib/statusteam-tickets`, владельцем назначьте `statusteam`, права `700`.
Файл конфигурации `/etc/statusteam-tickets.env` храните с правами `600`, владельцем root:

```dotenv
PAYMENT_PROVIDER=yookassa-test
TICKETING_BASE_URL=https://tickets.example.ru
TICKETING_HOST=127.0.0.1
PORT=4320
TICKETING_TRUST_PROXY=1
TICKETING_DB=/var/lib/statusteam-tickets/tickets.sqlite
TICKETING_STAFF_PASSWORD=REPLACE_WITH_RANDOM_PASSWORD_AT_LEAST_24_CHARS
YOOKASSA_SHOP_ID=TEST_SHOP_ID
YOOKASSA_SECRET_KEY=test_REPLACE_WITH_TEST_KEY
SMTP_URL=smtps://USER:PASSWORD@SMTP_HOST:465
MAIL_FROM=STATUS TEAM <tickets@example.ru>
```

Замените домены, параметры SMTP и тестовые ключи. Спецсимволы в логине/пароле SMTP URL
нужно кодировать как URL-компоненты. Отправитель должен быть разрешён почтовым провайдером.

В `ticketing/deploy/` подготовлены примеры systemd и Nginx. Проверьте путь `/usr/bin/node`
(это должен быть Node 24+), домен и пути сертификатов. Скопируйте service в
`/etc/systemd/system/statusteam-tickets.service`, настройте Nginx для поддомена и HTTPS.
Сначала выпустите сертификат; Nginx не запустится с путями к несуществующим файлам.

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now statusteam-tickets
sudo nginx -t
sudo systemctl reload nginx
```

Порт 4320 доступен только локально. Браузер и ЮKassa обращаются через HTTPS/443.
`TICKETING_TRUST_PROXY=1` разрешайте только за своим Nginx, который перезаписывает X-Real-IP.
Не включайте логирование полных URL заказа/билета: они содержат секрет доступа.

## 3. Подключить тестовую ЮKassa

1. Создайте **тестовый магазин** в ЮKassa.
2. Внесите его `shopId` и `test_...` ключ в серверное окружение.
3. В настройках HTTP-уведомлений тестового магазина укажите:
   `https://tickets.example.ru/api/webhooks/yookassa-test`.
4. Подпишитесь на `payment.succeeded`, `payment.canceled`, `refund.succeeded`.
5. Перезапустите service. Проведите тестовую покупку, отмену и возврат.
6. Вернувшись с оплаты, нажмите «Проверить оплату», если webhook ещё не пришёл.

Документация:

- [Тестовый магазин](https://yookassa.ru/docs/support/merchant/payments/implement/test-store).
- [Тестирование платежей](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing).
- [Быстрый старт API](https://yookassa.ru/developers/payment-acceptance/getting-started/quick-start).
- [HTTP-уведомления](https://yookassa.ru/developers/using-api/webhooks).

Тестовый адаптер написан по API, но без ключей тестового магазина внешняя интеграция здесь
не выполнялась. СБП и настоящие фискальные чеки локальная демонстрация не проверяет.

## 4. Что требуется до реальной продажи

1. Утвердить юрлицо-продавца, банк/провайдера, расчётный счёт, договор эквайринга.
2. Подтвердить категории, цены, количество билетов, дату/время и площадку.
3. Выбрать кассу и реализовать чеки оплаты/предоплаты, зачёта, возврата и контроль ошибок.
   Поля НДС и способов расчёта согласовать с бухгалтером. QR-билет не заменяет чек.
4. Подготовить оферту, правила возврата, реквизиты и документы/настройки обработки персональных данных.
   Эта демонстрация не собирает юридически значимое согласие и не содержит готовых документов продавца.
5. Добавить и проверить production-адаптер выбранного банка, отдельный production webhook,
   процедуру сверки и обработки спорных платежей. Простая замена test-ключа не откроет live-режим.
6. Провести полную покупку/возврат с фискальными чеками; проверить доставку почты, резервные копии
   и восстановление базы, доступ персонала, тест на реальной нагрузке.
7. Только затем указать URL своего checkout в `src/content/event.ts`, включить `SALES_OPEN`,
   пересобрать статический сайт и опубликовать его на Beget.

## Ограничения и эксплуатация

- Продажа по категориям, без закреплённых кресел. Рассадка требует отдельной модели мест.
- Возврат только всей суммы заказа. Использованные билеты требуют ручного разбора, автоматический возврат блокируется.
- Все служебные действия пока доступны одной учётной записи. Для нескольких сотрудников/реальных продаж нужны роли,
  персональные учётные записи, журнал действий и отдельная политика доступа к возвратам.
- Резерв снимается только после подтверждённой отмены или возврата. При сбое банка резерв сохраняется;
  автоматического снятия через 15 минут нет — это предотвращает перепродажу ещё оплачиваемого билета.
- Повторная проверка выполняется раз в минуту, до 100 незавершённых заказов за проход. Для большого объёма
  нужна очередь с расписанием попыток и мониторинг зависших резервов.
- SQLite — один сервер/процесс и локальный диск. Не используйте общий сетевой диск и несколько реплик.
  Ежедневно делайте согласованную копию средствами SQLite backup, а не копированием одного `.sqlite` при активном WAL.
- Ссылки на заказ/билет являются секретами. Для потерянной ссылки — повторная отправка из защищённой админки.
- Почта отправляется с постоянным Message-ID. При сбое после SMTP-приёма письмо может прийти повторно;
  дополнительные билеты не создаются. В этой версии письмо содержит ссылку, а не PDF-вложение.
- Камера использует BarcodeDetector, доступный не во всех браузерах. Есть ручной ввод и USB-сканер
  (вводит код как клавиатура). Сканирование на выбранных телефонах требуется проверить; offline-входа нет.
- После отменённого банком возврата требуется ручная проверка; повторный новый возврат для такого кейса пока не реализован.
