## Схема резерва — предложение для согласования перед запуском

- Один заказ = один билет, серверная цена 1 000 000 копеек, RUB, лимит 100.
- Место резервируется транзакцией MySQL **до** обращения к провайдеру.
- Автоматического срока заказа 15 минут **нет**. Платёж `pending` может ещё
  оплачиваться; место удерживается, включая таймауты API и поздний webhook.
- Освобождение только после проверенного через API окончательного `canceled`.
- `capture=true`: одностадийная оплата. Параметр `expires_at` двухстадийного
  подтверждения не используется как срок бронирования/платёжной страницы.
- `waiting_for_capture` неожиданен для этой схемы: билет не выдаётся, резерв
  остаётся, сотрудник проверяет магазин. Автоматического capture нет.
- Неизвестный результат создания повторяется с **тем же телом и ключом** до
  23 часов. Затем `manual_review`: место не освобождается, новый платёж не создаётся.
  Гарантия идемпотентности провайдера — 24 часа, оставлен запас.
- После ручного поиска платежа в кабинете его ID можно подставить в соответствующую
  запись `payments` по UUID из metadata только после сверки магазина/суммы/режима;
  затем Cron запросит объект через API. Не удаляйте резерв ради восстановления продаж.
- Возвращённое место автоматически не возвращается в продажу.

Это консервативная схема: неоплаченные резервы могут временно уменьшать доступный
остаток. Для короткого резерва потребуется отдельно согласовать реально доступный
способ отмены платёжной сессии. Не ставить TTL 15 минут отдельно от платёжной логики.

## 1. Подтвердить среду у Sprinthost

В публичной базе знаний указаны PHP 8.4/8.5 и MySQL 5.7/8.0. **Фактически выбранные
версии этого аккаунта неизвестны.** Выбрать PHP 8.4 или 8.5 для сайта и Cron.
Запросить полный путь CLI PHP, версию MySQL и расширения: PDO MySQL, curl,
mbstring, sodium, OpenSSL, SimpleXML. Требуются InnoDB, транзакции и row locks.
Разработка и конкурентные проверки выполнены на MySQL 8.4.7/PHP 8.4.24.

Зафиксированы PHPMailer 7.2.0 и Endroid QR Code 6.0.9; транзитивные зависимости —
`backend/composer.lock`. Endroid 6 выбран для PHP 8.4; не заменять слепо последней
major-версией с другими требованиями. Не игнорировать platform requirements.

Подтвердить у поддержки SMTP host/port/encryption для `tickets@statusteam-official.ru`.
Ошибка IMAP в веб-почте ничего не доказывает о работоспособности SMTP.

## 2. Разложить каталоги

Обозначения: `DOMAIN_DIR` — подтверждённый абсолютный каталог домена, в нём уже
есть `public_html`. `STATUS_PHP` — подтверждённый полный путь PHP 8.4/8.5.
Это переменные для примера, **не готовые пути аккаунта**.

```text
DOMAIN_DIR/
  public_html/                существующие файлы out/
    api/                      только backend/public/* и его .htaccess
  status-backend/             приватный backend/ (src, vendor, migrations, bin, config.php)
```

Не загружать весь репозиторий в public_html. Приватный каталог находится рядом с
public_html, а не внутри него. В `public_html/api/index.php` по умолчанию используется
`dirname(__DIR__, 2).'/status-backend/bootstrap.php'` — проверьте соответствие.
Для другой структуры измените **только этот путь**. Убедитесь, что поддомены и
дополнительные сайты также не публикуют приватный каталог.

На доверенной машине сборки:

```bash
npm ci
npm run backend:assets
composer install --working-dir=backend --no-dev --prefer-dist --no-interaction
composer check-platform-reqs --working-dir=backend
composer audit --working-dir=backend
```

На хостинг передать backend с vendor; `backend/public` скопировать в api вместе с
`.htaccess`, `app.js`, `app.css`, `scanner.min.js`, `scanner-LICENSE`.
Сканер ZXing Browser 0.1.5 собирается локально, CDN посетителям не нужен.
Composer можно запускать на самом хостинге, если доступен совместимый CLI.

Проверить HTTPS, отсутствие листинга и невозможность скачать config.php, vendor,
SQL, журналы и `page.php`. Прямой запрос `api/page.php` должен давать 403/404.
Не устанавливать публичный install.php/phpinfo.php. Установщик — только CLI.

## 3. Закрытая конфигурация

Скопировать `config.example.php` → `status-backend/config.php`, права 600;
приватный каталог 700, учётная запись PHP должна иметь доступ. Не отправлять файл
в Git, клиентскую сборку или чат. Создать случайный ключ командой из примера и
сохранить отдельно в защищённой резервной копии. Потеря ключа делает зашифрованные
заявки и билеты нечитаемыми. Пароли БД/SMTP, секрет магазина вносит владелец сам.

БД: localhost, `a1325854_data`, пользователь `a1325854_data`; пароль — только
в приватном конфиге. Для теста и боевого магазина нужны **разные БД, конфиги и ключи**.
Если доступна только одна БД — не запускать тестовый reset-скрипт в ней; создать
отдельную тестовую БД. `backend/tests/run.php` специально требует суффикс `_test`
и `TEST_ALLOW_RESET=yes`, потому что удаляет таблицы тестовой базы.

Заполнить подтверждённые `origin`, `base_url`, поддержку и получателя уведомлений.
origin без завершающего `/`. Поддержка не выдумана: пока поле пусто, checkout закрыт.
`application_recipient` — согласованный почтовый ящик в российской инфраструктуре.
Уведомление о заявке не содержит её персональных данных: сотрудник читает их в кабинете.
`trusted_proxies=[]` по умолчанию: X-Forwarded-For игнорируется. Вносить только точные
IP прокси Sprinthost после подтверждения их реальной цепочки, не весь интернет.

```bash
"$STATUS_PHP" "$DOMAIN_DIR/status-backend/bin/console.php" preflight
"$STATUS_PHP" "$DOMAIN_DIR/status-backend/bin/console.php" migrate
"$STATUS_PHP" "$DOMAIN_DIR/status-backend/bin/console.php" staff-add administrator admin
"$STATUS_PHP" "$DOMAIN_DIR/status-backend/bin/console.php" staff-add door1 controller
```

Пароль вводится скрыто интерактивно, не в аргументах команд. Каждый контролёр
получает отдельную учётную запись. Отключение: `staff-disable door1`.
Миграции выполняются один раз с checksum; если DDL оборвался, MySQL не откатывает
CREATE TABLE. Остановиться, восстановить тестовую копию или исследовать частичную
миграцию, не запускать её многократно поверх неизвестной схемы.

## 4. Документы и формы

Не включать `documents_approved`, пока юрист не подтвердит актуальные тексты.
Для каждой редакции сохранить точную копию опубликованного текста:

```bash
"$STATUS_PHP" "$DOMAIN_DIR/status-backend/bin/console.php" document-import terms VERSION /documents/terms/ /private/approved-terms.txt
```

Повторить для privacy, offer, buyers, casting, partner, press; guardian — только после
подтверждения отдельной редакции представителя. VERSION и href установить теми же
в `src/content/legal.ts`, опубликовать **тот же** утверждённый текст/файл, пересобрать.
Сервер сохраняет полный текст, SHA-256 и редакцию; журнал ссылается на неё по FK.
Старая редакция не перезаписывается. Переключение active сериализовано с отправкой
форм через блокировку inventory. Клиентское время не используется для журнала.

Пока guardian не опубликован, `minor_forms_enabled=false`. Добавлены ФИО, статус,
телефон, e-mail представителя и подтверждение полномочий; паспорта не загружаются.
Основание набора полей — раздел 7 существующего черновика casting, а не новый
юридический текст. Отдельная редакция guardian требует решения юриста.

Для заявок включить `forms_enabled=true` только после проверки всей российской
инфраструктуры. Подписка отключена на клиенте и сервере; double opt-in и рекламные
рассылки **не реализованы**, пользовательские рекламные адреса не собираются.

Сборка российского сайта: `NEXT_PUBLIC_FORM_ENDPOINT=/api/index.php?r=forms`.
В Workers-preview значение пустое; дополнительно клиент не отправляет запросы
с доменов, отличных от `statusteam-official.ru`, и запрещает cross-origin endpoint.
Никаких реальных данных на Workers, D1, KV, GitHub, CDN-антиботы не отправляется.
Защита форм: серверные лимиты по HMAC IP, лимит тела, honeypot, строгая валидация,
идемпотентность и same-origin. Это базовая защита; при целевой распределённой атаке
подключить ограничение трафика у российского хостера. Публичный CORS не открывать.

## 5. Тестовый магазин и фискальные настройки

Внести **тестовые** shop_id/secret, `environment=test`, `yookassa.test=true`.
На тестовом сервере разрешить checkout только для проверяющего; реальный домен
пока не публикуется из этой ветки. В текущем браузерном клиенте разрешён только
основной домен: для отдельного российского staging нужен явно проверенный домен
в `api.ts`, соответствующие origin/base_url и тестовая сборка. Не включать Workers.
`CHECKOUT_ENABLED=false` остаётся в репозитории; для закрытой проверки подготовить
отдельную локальную сборку и конфиг после публикации тестовых редакций документов.

Фискальные настройки не выдуманы. У бухгалтера/ЮKassa уточнить:

1. Какое решение используется: «Чеки от ЮKassa» или сторонняя онлайн-касса; договор,
   подключение кассы, данные продавца, e-mail покупателя, кто реально отправляет чек.
2. Система налогообложения (`tax_system_code`), ставка (`vat_code`), предмет расчёта
   (`payment_subject`), способ расчёта (`payment_mode` и `refund_payment_mode`).
3. Считается ли оплата билета полным расчётом или предоплатой; нужен ли закрывающий
   чек после оказания услуги. Не выбирать ответ по своему усмотрению.
4. Правило частичного возврата, судьба билета, подтверждение суммы и бухгалтерские
   документы по удержаниям. Автоматической шкалы удержаний в коде нет.

Реализован сценарий **платёж+чек в одном запросе**, возврат+чек в одном запросе.
В receipt передаётся одна позиция, quantity=1.00, серверная сумма; для возврата —
фактически возвращаемая сумма. `receipt_registration` сохраняется и виден админу.
Выбор `integration` другого типа блокируется. Корректность параметров именно для
договора магазина должна быть проверена тестом вместе с ЮKassa/бухгалтером.

**Закрывающие чеки зачёта предоплаты пока не реализованы.** Боевая оплата при
payment_mode, отличном от full_payment, блокируется независимо от остальных флагов.
Если бухгалтер определит предоплату, нужен отдельный этап реализации closing receipt;
одним переключением флага такой магазин запускать нельзя.

Полный возврат аннулирует билет. Частичный по умолчанию запрещён. После утверждения
выбрать `partial_refund_policy=keep` (остаётся действующим) или `void` (аннулируется).
На время неопределённого/ожидающего возврата проход блокируется. Отмена возврата
восстанавливает право прохода, если билет не использован и нет другого основания
аннулирования. Возвраты из кабинета ЮKassa принимаются через webhook и перепроверяются;
если webhook потерян, сверка refunded_amount блокирует проход до выяснения.
Для восстановления внешнего возврата: `console.php refund-sync PROVIDER_REFUND_ID`.
Никогда не создавать новый возврат вслепую после таймаута.

## 6. Webhook и точные маршруты

В тестовом кабинете ЮKassa → Интеграция → HTTP-уведомления:

`https://statusteam-official.ru/api/index.php?r=webhook`

События: `payment.succeeded`, `payment.canceled`, `payment.waiting_for_capture`,
`refund.succeeded`. Для отдельного staging подставить его российский HTTPS-домен.
HTTP Basic Auth использует настройку уведомлений в кабинете, не API OAuth webhooks.

Уведомление — только сигнал для GET объекта через API с нашими credentials.
Проверяются ID, metadata.order_id, recipient.account_id, сумма/валюта, test и paid.
Return URL ничего не подтверждает. Для повторов есть UNIQUE(order_id) билета и
транзакция оплаты/билета/outbox. Ошибка проверки возвращает не-2xx; оповещения не
логируют тела. На web-сервере не включать запись POST body или Authorization.

| Маршрут `api/index.php?r=...` | Метод | Назначение |
|---|---|---|
| forms | POST JSON | модели, партнёры, СМИ |
| orders | POST JSON | один заказ и платёж |
| order-status | POST JSON | статус по capability `token` |
| webhook | POST JSON | уведомление ЮKassa |
| ticket / return | GET | оболочка билета / статуса; capability только после `#` |
| ticket-data | POST JSON | данные билета и локальный QR; не погашает |
| staff | GET | кабинет входа |
| session / login / logout / me | POST JSON | сессия и доступ |
| check / admit | POST JSON | проверка / отдельное погашение; сотрудник+CSRF |
| dashboard / application-detail | POST JSON | заявки, статусы, очередь; только admin |
| refund / resend / mail-retry | POST JSON | возврат, тот же билет, повтор письма; admin+CSRF |

Публичные формы требуют Origin, совпадающий с конфигурацией. API проверяет
Content-Type JSON и лимит 32 KiB. Карточные реквизиты не проходят через сайт.
Для forms обязательны requestKey (64 hex), form, поля формы, termsAccepted=yes,
consent=yes, consentDocuments=[{id,version}]. Для orders — name/email/phone,
termsAccepted=yes и редакции terms/offer/buyers/privacy. Цена/статус из браузера игнорируются.
`quantity` из старого hidden-поля также игнорируется: заказ всегда из одного билета.

## 7. SMTP и Cron

Внести подтверждённые host/port/tls либо ssl; не отключать TLS verification.
Отправитель `tickets@statusteam-official.ru`. Проверить:

```bash
"$STATUS_PHP" "$DOMAIN_DIR/status-backend/bin/console.php" smtp-test YOUR_CONTROLLED_MAILBOX
```

Это служебное тестовое письмо без покупателя. Успешный SMTP-ответ подтверждает
только приём сервером: проверить Входящие/Спам, заголовки SPF=pass, DKIM=pass,
DMARC=pass, доставку на несколько согласованных почтовых сервисов. SPF/DKIM выдаёт
Sprinthost; не придумывать записи и не заменять существующий SPF вторым. Согласовать
DMARC-политику с администратором домена. DNS этой веткой не меняется.

В панели Cron подставить подтверждённые **абсолютные** пути, без переменных из SSH:

```cron
* * * * * /CONFIRMED/PHP84 /ABSOLUTE/DOMAIN_DIR/status-backend/bin/console.php mail >> /PRIVATE/status-mail.log 2>&1
* * * * * /CONFIRMED/PHP84 /ABSOLUTE/DOMAIN_DIR/status-backend/bin/console.php reconcile >> /PRIVATE/status-reconcile.log 2>&1
*/5 * * * * /CONFIRMED/PHP84 /ABSOLUTE/DOMAIN_DIR/status-backend/bin/console.php health >> /PRIVATE/status-health.log 2>&1
```

Логи — вне public_html, права 600, ротация и контроль размера. PHP-команды выводят
только счётчики и фиксированные коды, без ФИО/почты/QR/ключей. На старте запускайте
каждую команду вручную с тем же PHP и правами. Параллельные mail-процессы используют
row lock и lease 5 минут; 10 попыток, затем failed. Повтор из кабинета не выпускает
новый билет. При обрыве после принятия письма SMTP возможна повторная доставка того
же письма/билета (at-least-once), а не новый действующий билет.

health показывает неполученные чеки, manual_review, failed и письма старше 45 минут.
Назначить живого ответственного, который контролирует эти значения и устраняет сбой
до обещанного часа. Автоматические внешние аварийные оповещения не настроены.
Нормальная доставка после оплаты занимает до следующего минутного Cron.

## 8. Инструкция контролёрам

Открыть `https://statusteam-official.ru/api/index.php?r=staff` по HTTPS. Войти в свою
учётную запись. «Включить камеру» → разрешить доступ → навести на QR. QR содержит
64-символьный код. Для ручной проверки также можно ввести напечатанный номер ST-...:
он ищется только в авторизованном кабинете, публично билет по номеру не открывается.
Если камера недоступна/разрешение отклонено, использовать ручной ввод либо другое
проверенное устройство. Нужен интернет; офлайн-проход не реализован.

«Действителен» ещё **не** означает погашение. Сверить билет и нажать «Подтвердить
проход». Только ответ «Проход подтверждён» означает успешную атомарную запись.
«Уже использован», «Возвращён», `refund_pending`, «не найден» — не пропускать,
передать администратору. Простое открытие ссылки билета и сканирование не гасят его.

Сессия: 30 минут бездействия, максимум 4 часа. После смены выйти. Отключённый в БД
сотрудник теряет доступ и в существующей сессии. Админ отдельно видит очереди,
открывает заявку по ID, отправляет существующий билет и подтверждает сумму возврата
двойным вводом. Перед возвратом сверять ID заказа в списке, не полагаться на имя.

## 9. Хранение, удаление, резервные копии

БД, ciphertext и резервные копии — в РФ. Ключ отдельно от выгрузок БД. Администраторы
БД/хостинга и доступы SSH ограничены; уникальные пароли, доступ по необходимости.
Приложение шифрует заявки, покупателей, контакты согласий, получателей писем и QR
secretbox; таблицы технических статусов и серверный IP журнала согласий остаются
доступны авторизованному администратору БД. Пароли сотрудников — password_hash.

До запуска юрист задаёт сроки по целям и основания хранения бухгалтерских документов.
В конфиге retention задаются утверждённые даты applications_before, orders_before,
consents_before. Пустые даты блокируют удаление, до окончания мероприятия purge
тоже заблокирован. Не использовать эти поля для произвольной ранней очистки.

Процедура: проверить основания и запрос, поставить hold для спора/обязательного
хранения (`console.php hold order ID dispute` или application), остановить Cron mail,
дождаться отсутствия sending, сделать закрытую резервную копию, выполнить `purge`
для просмотра **счётчиков**, сверить их, затем `purge --apply`. Удаляются связанные
контакты согласий, заявки/покупатели, mail outbox, платежи, возвраты и QR; документы
редакций сохраняются. Заказы с pending refund и действующие резервы не удаляются.
Обезличенный staff_audit с UUID остаётся для служебного аудита.

Индивидуальные запросы до срока рассматриваются ответственным по основанию и hold;
для выборочного удаления использовать согласованную процедуру на закрытой БД с тем
же порядком зависимостей, не публичную форму и не общие логи. Медицинские документы
здесь не принимаются.

У Sprinthost подтвердить расположение и сроки backup, доступ, уничтожение копий и
процедуру восстановления. Зафиксировать утверждённый срок отдельно в регламенте.
Не обещать удаление из backup немедленно, если провайдер этого не обеспечивает.
При восстановлении старой копии до возврата в работу повторить удаления/отзывы по
закрытому журналу запросов. Этот процесс хостинга код автоматически не выполняет.

## 10. Перед боевым запуском остаётся вручную

- Подтвердить реальные PHP/MySQL/расширения и файловые права; применить миграции в РФ.
- Согласовать предложенный бессрочный до final cancel резерв и позднюю оплату.
- Утвердить/опубликовать документы и snapshot-редакции, поддержку, получателей и сроки.
- Сверить несовпадения черновиков: старое шоу «Славянский взгляд», placeholders даты,
  подрядчиков и площадки; в terms сейчас раздел 7, отдельная оферта продажи отсутствует.
  Подготовлен пустой ID offer и обязательная ссылка в checkbox/серверной проверке:
  разместить утверждённую отдельную оферту (например PDF), задать href/version
  и импортировать snapshot. Тексты самостоятельно не переписаны.
- Подтвердить guardian, сверить перечень фактически собираемых полей с документами.
- Подключить кассу/чеки, получить ответы бухгалтера. Предоплата требует closing receipt.
- Проверить тестовым магазином реальный redirect/webhook, статус, сумму, refund, чек,
  повторные события, Cron при потере webhook и доставку SMTP. Реальных списаний не было.
- Проверить камеру на реальных iPhone/Android, доступы и интернет на площадке.
- Назначить мониторинг, обучение сотрудников, backup/retention и регламент возвратов.
- Лишь после отдельного разрешения подготовить production config/сборку, снять
  клиентский и серверный запреты, перенести backend и out. Эта ветка ничего не
  публикует на рабочий домен и не меняет DNS.

## 11. Маршрут данных для юриста

После установки: браузер → HTTPS на Sprinthost в РФ → PHP этого репозитория → MySQL
на Sprinthost (заявки, журнал согласий, заказы, платежи, QR-токены, возвраты, проходы,
очередь). Уведомления и ссылки билетов → SMTP Sprinthost от tickets@statusteam-official.ru.
Покупатель перенаправляется на ЮKassa, сервер передаёт ей ID/сумму заказа и e-mail
для чека; ЮKassa/подключённая касса формируют чеки по выбранному договору. Билет
генерируется собственным PHP-кодом, QR — локальной библиотекой Endroid. Доступ
сотрудников к заявкам и билетам авторизован. CRM, внешняя рассылка и облачное
хранилище QR не используются. Юрлица/ИНН/адреса подрядчиков сверить с договорами.

**Сейчас это маршрут подготовленного кода, а не подтверждение установки на production.**
Статический Workers-preview не принимает реальные данные. Российское размещение,
SMTP, касса и подрядчики требуют подтверждения владельцем инфраструктуры.

### Точные расхождения черновиков и интерфейса для юриста

| Место | Расхождение / решение перед запуском |
|---|---|
| Черновики casting/press | Упоминают «Славянский взгляд»; продаётся «Пульс Континента» |
| Редакции | Дата `[__] ноября`, placeholders подрядчиков — нельзя считать утверждёнными |
| casting | В форме возраст, а в тексте дата рождения; в форме ссылки на материалы, а в тексте загружаемые фотографии; загрузки файлов здесь нет |
| guardian | Набор полей из раздела 7 casting добавлен, отдельная утверждённая редакция ещё отсутствует |
| terms / offer | В имеющемся тексте продажи в разделе 7; отдельной оферты нет. ID offer подготовлен, публикация/согласование требуется |
| Рассылка | Черновики существуют, но сбор адресов и рассылка отключены |
| Срок оплаты | В коде нет TTL заказа 15 минут; согласовать удержание до проверенного canceled |
| Чеки | Поддерживается совместная отправка receipt; выбор предоплаты требует ещё не реализованных закрывающих чеков |

Если утверждённый документ публикуется отдельным PDF, его href имеет приоритет:
страница документа показывает ссылку на утверждённый файл, а не старый черновик.
Для публикации текста по `/documents/ID/` необходимо также заменить соответствующий
черновик на **предоставленную юристом** утверждённую редакцию. В этой ветке этого не делали.
